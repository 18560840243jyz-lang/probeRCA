# A0 Label Leakage and Architecture Gap Audit

## Executive Summary
中文解释：执行摘要。

- current implementation category: **probeRCA-PoC / partial implementation**
- label leakage risk: **HIGH**
- blind RCA status: **FAIL** for current P2E results; **NOT_VERIFIED** for a target-evidence-disabled rerun
- architecture completeness: **DEGRADED**

The current codebase has real single-VM Online Boutique fault injection, real metric collection, and a working P1-style RCA pipeline. However, the P2 real experiments are not blind RCA experiments. The most important issue is that P2 `evidence.jsonl` records are generated by fault-specific code using known target/root service and target/root metric information, then consumed by `proberca/evidence/ipw_semantic.py` as semantic evidence that directly boosts candidate scoring. This is a configuration-derived evidence leakage risk.

Root labels are generally not used directly by the core sparse ranking or final `p1_results.jsonl` construction, but they are used for incident windows, debug/evaluation, and P2 target-specific evidence generation. Therefore the 20-repeat P2E result can support a PoC statement about real injected data under a target-aware evidence protocol, but it cannot support a claim of fully blind RCA accuracy or a complete original probeRCA implementation.

## Key Findings

1. **P2 evidence generation is target/root directed.** CPU, Network, I/O, and Lock evidence builders all write evidence for the known target/root service and metric family, not for a blind set of competing services.
2. **Semantic scoring consumes that evidence and changes ranking.** `ipw_semantic.py` builds an evidence index by `(incident_id, service, evidence_type)` and multiplies sparse scores by evidence strength.
3. **Incident windows are provided by injection scripts.** `start_ts`/`end_ts` are used by normalization, propagation, and bridge code. There is no implemented alert gate or automatic incident-window builder.
4. **Root labels are mostly restricted to evaluation/debug in core P1 modules.** `ipw_sparse.py`, `ipw_semantic.py`, `ipw_path.py`, and `p1_metrics.py` use root labels mainly after scoring for debug/evaluation summaries.
5. **P1 final RCAResult does not include true labels.** `p1_result.py` builds outputs from semantic/type/path records and does not emit `root_service`, `root_metric`, or `injected_path`.
6. **Path explanation uses `injected_path` only for debug fidelity checks, not for path search.** It does use `symptom_service` from incident records, which is acceptable if interpreted as alert context.
7. **P2 lock experiments are real sidecar lock-stress, not an original cartservice business-code bug.** This is documented and should remain in claims.
8. **Implementation is a PoC and not complete probeRCA.** Alert gate, adaptive probe controller, eBPF probes, online storage, counterfactuals, full sparse optimization, and UI are missing or degraded.
9. **Current P2E Top3 accuracy is valid only under the current target-aware evidence protocol.** It should not be presented as fully blind RCA accuracy.
10. **A blind rerun is required before claiming blind RCA.** The rerun must disable target-derived evidence and provide only metrics, service graph, symptom/alert window, and non-target-specific observed evidence.

## Evidence Generation Leakage Risk

### Overall conclusion

- evidence 是否来自真实观测指标？ **Partly yes.** Evidence scores are often based on real metric lift, especially Network/I/O/Lock and repaired CPU cAdvisor metrics.
- evidence 是否由实验配置 target_service/target_metric 定向生成？ **Yes.** Evidence is written only for the known target/root service and target metric family.
- evidence 是否会帮助 RCA 直接命中目标服务？ **Yes.** `ipw_semantic.py` applies service/evidence-type evidence as a score multiplier/bonus, which can directly promote the known target service.
- 当前 P2 结果是否可以称为 blind RCA？ **No.** It is target-aware real-injection RCA under a PoC evidence protocol.
- 如果不能，原因是什么？ The evidence generation chain uses known injected target/root service and metric information, and incident windows are supplied by injection scripts rather than discovered by an alert module.

### CPU

- Files: `proberca/adapters/online_boutique/p2a1_cpu_experiment.py`, `p2a3_cpu_repeat.py`, `p2a2_real_rca.py`
- Key lines:
  - `p2a1_cpu_experiment.py:143-158` builds incident root labels from config fields `target_service`, `target_metric`, `target_fault_type`.
  - `p2a1_cpu_experiment.py:194-227` builds CPU evidence specifically for `paymentservice.cpu.throttled_usec`.
  - `p2a1_cpu_experiment.py:206-208` writes weak evidence score `0.05` even when lift score is zero.
  - `p2a2_real_rca.py:88-95` passes this evidence into the frozen P1 pipeline.
- Risk: **HIGH**
- Explanation: CPU evidence is based on real cAdvisor lift when present, but service and metric are hardcoded/target-derived. It is not generated for all competing CPU services. It enters semantic scoring and can help target the root service. CPU exact Hit@1 instability is real and reported, but the Top3 success is still not blind.

### Network

- File: `proberca/adapters/online_boutique/p2b1_network_repeat.py`
- Key lines:
  - `p2b1_network_repeat.py:277-305` uses `incident["root_service"]` to write Net evidence for the root service only.
  - `p2b1_network_repeat.py:309-324` builds the incident with `root_service="shippingservice"`, `root_metric="net.retrans"`, and `injected_path`.
  - `p2b1_network_repeat.py:491-495` writes `incidents.jsonl` and `evidence.jsonl` before RCA.
- Risk: **HIGH**
- Explanation: Evidence score is derived from real `net.retrans`/`net.rtt_ms` lift, but it is directed to the known root service. There is no same-type evidence generated for non-target network services as a blind comparison.

### I/O

- File: `proberca/adapters/online_boutique/p2c1_io_repeat.py`
- Key lines:
  - `p2c1_io_repeat.py:267-297` uses `incident["root_service"]` to write I/O evidence for the root service only.
  - `p2c1_io_repeat.py:301-316` builds the incident with `root_service="redis-cart"`, `root_metric="io.write_bytes"`, and `injected_path`.
  - `p2c1_io_repeat.py:509-513` writes raw metrics, incident labels, and target-directed evidence.
- Risk: **HIGH**
- Explanation: Evidence score is derived from real write-bytes/write-ops/io-time lift, but the evidence target is known from the injected incident. It can directly help semantic scoring select `redis-cart`.

### Lock

- File: `proberca/adapters/online_boutique/p2d1r_lock_repeat.py`
- Key lines:
  - `p2d1r_lock_repeat.py:59-88` converts phase-aware sidecar logs into real baseline/faulty/recovery lock metrics.
  - `p2d1r_lock_repeat.py:123-164` uses `incident["root_service"]` to write Lock evidence for `cartservice` and assigns `evidence_score=1.0` when lift is positive.
  - `p2d1r_lock_repeat.py:167-180` builds root labels and injected path.
  - `p2d1r_lock_repeat.py:323-327` writes incidents and evidence before RCA.
- Risk: **HIGH**
- Explanation: Phase-aware baseline metrics are real idle sidecar measurements, not fake zeros. However, evidence is still target/root directed and given a strong score for the known cartservice sidecar lock fault.

### Semantic scoring impact

- File: `proberca/evidence/ipw_semantic.py`
- Key lines:
  - `ipw_semantic.py:95-115` builds normalized evidence by `(incident_id, service, evidence_type)`.
  - `ipw_semantic.py:238-257` reads evidence by candidate service/type and computes `semantic_score = sparse_score * (1 + evidence_weight * evidence_score) * specificity + anchor_bonus + priority_bonus`.
- Risk: **HIGH as leakage amplifier**
- Explanation: The scorer itself does not read `root_service` or `root_metric` for scoring, but it trusts `evidence.jsonl`. If `evidence.jsonl` is target-derived, semantic scoring amplifies leaked target information.

## Incident Label Usage Audit

### Modules reading `incidents.jsonl`

The grep audit shows `incidents.jsonl` is read by normalization, observation, propagation, sparse inversion, semantic scoring, path explanation, final result building, evaluation, and P2 bridge/repeat modules.

### Use of `start_ts` / `end_ts`

- `proberca/features/robust.py:55-60`, `80-93`, `127-134`, `155-162`: uses `start_ts`/`end_ts` to choose baseline and faulty records.
- `proberca/propagation/ipw.py:118-149`, `293-398`: uses incident windows to build baseline/faulty propagation residuals.
- `proberca/adapters/online_boutique/p1_bridge.py:47-70`: uses incident windows to assign observed metrics to baseline or incident.

Conclusion: **The current pipeline depends on injection-provided incident windows.** There is no implemented automatic alert module or change-point/SLO gate that discovers windows from metrics.

### Use of `root_service` / `root_metric` / `root_type`

- Allowed evaluation/debug:
  - `proberca/eval/p1_metrics.py:41-48`, `65-83`: uses root labels and injected path for metrics/debug only.
  - `proberca/inference/ipw_sparse.py:252-268`: computes `true_root_rank_debug` after candidate ranking.
  - `proberca/evidence/ipw_semantic.py:288-306`: computes true-root semantic debug rank/score after ranking.
- Suspicious target-directed evidence:
  - P2 evidence builders use root/target labels to construct `evidence.jsonl` before semantic scoring.

Conclusion: **Root labels do not appear to directly sort P1 sparse candidates or final RCAResult, but target/root-derived evidence enters semantic scoring.**

### Use of `injected_path`

- `proberca/explain/ipw_path.py:265-269`, `327-330`: checks whether the selected path intersects injected path for summary/debug.
- `proberca/eval/p1_metrics.py:22-25`, `47-83`: uses injected path for path_fidelity evaluation.

Conclusion: `injected_path` appears to be used for debug/evaluation, not path search. Path search uses candidate service, symptom service, service graph, and propagation support.

## Validity of Current P2 Accuracy

1. **故障注入是否真实？** Yes. CPU resource limits, tc netem, Redis-cart dd/sync I/O stress, and cartservice sidecar lock contention are real single-VM kind injections.
2. **指标采集是否真实？** Yes, for the implemented collectors: kubelet/cAdvisor, `/proc/net/snmp`, `ss` when available, frontend curl latency, cAdvisor fs metrics, and sidecar stdout lock metrics.
3. **RCA 是否完全盲？** No.
4. **是否有可能由 target-specific evidence 帮助定位？** Yes. P2 evidence is generated for the known target/root service and is consumed by semantic scoring.
5. **当前 20 次 P2E 结果可以怎么表述？**
   - 可以说："在 Online Boutique 单机伪分布式真实注入数据上，当前 probeRCA-PoC pipeline 在 target-aware evidence protocol 下，按 P2 Top3 口径完成了 20 次 RCA 验证。"
   - 可以说："故障注入和指标采集是真实的；P2 主指标 service Hit@1、metric Hit@3、root type accuracy、path fidelity 在当前协议下为 1.0。"
6. **当前 20 次 P2E 结果不能怎么表述？**
   - 不能说："完整 probeRCA 在线系统已验证。"
   - 不能说："自动报警、自适应 eBPF、传播漂移和完整稀疏反演均已实现。"
   - 不能说："完全盲 RCA 准确率为 100%。"
   - 不能说："Lock fault is an original cartservice business-code bug."

## Required Fixes Before Claiming Full probeRCA

1. Implement or simulate an alert gate that derives `start_ts`/`end_ts` from metrics/SLO/change-point, rather than injection labels.
2. Run a blind RCA protocol that gives the pipeline only metrics, service graph, symptom/alert context, and alert window; withholds root labels, target labels, injected path, and target-specific evidence.
3. Replace target-directed P2 evidence builders with blind evidence extraction over all observed services/metrics, or disable evidence for the blind baseline.
4. Ensure `evidence.jsonl` is generated from observed measurements without using `target_service`, `target_metric`, `root_service`, `root_metric`, `root_type`, or `incident_id`-specific special cases for scoring.
5. Add an evidence trust-boundary check: semantic scoring should reject or flag evidence produced from ground-truth experiment config.
6. Implement a candidate subgraph builder from symptom service and topology/resource relationships.
7. Implement real adaptive probe control and/or real eBPF observation if claiming full architecture.
8. Implement or clearly defer optional propagation drift, full sparse optimization, counterfactual explanation, online storage/query, and UI.
9. Rerun P2 blind experiments and report primary metrics separately from current target-aware PoC metrics.
10. Keep CPU exact Hit@1 instability and lock sidecar limitation explicit in all summaries.
